# 旧式直接 SQLite 路线：实现归档与风险边界

这份归档记录旧工具曾经采用的思路，便于审计、迁移和复盘。它认可该方法在受控离线场景中的实用价值；同时不包含可以对任意用户资料库直接写入的脚本。完整的操作契约见 [controlled-offline-direct-write.md](controlled-offline-direct-write.md)。

## 曾经的工作流

```text
计划 JSON（父收藏夹、日期分组、条目 key/DOI/标题）
    ↓
关闭 Zotero，备份 SQLite
    ↓
旧脚本直接 INSERT collections / collectionItems
    ↓
旧脚本自行生成八位对象 key，并手工标记为待同步
    ↓
启动 Zotero 并尝试同步
```

## 这次同步故障暴露的条件缺口

1. 旧代码最初使用 `A-Z` 和 `0-9` 随机生成 key；其中 `0`、`1`、`I`、`O` 会导致服务端拒绝新对象 key。后续生成器已经修正字符集，但历史对象仍需按同步状态与范围谨慎处理。
2. 即使避开字符问题，直接写库仍需要维护对象版本、缓存、删除墓碑、附件和引用完整性；这不是“方法错误”，而是对内部模型的维护要求。
3. 手工补写同步缓存或同步版本必须与当时的 Zotero 版本及对象全貌一致；只修一张表会造成不可预测的同步表现。
4. 直接把 PDF 复制到 `storage` 目录并插入附件行，可以完成本机附件登记，但并不等于完成服务端附件上传。

## 可保留的非危险思想

- 在改变前建立完整备份；
- 将批量任务写成 JSON 计划并先做 dry-run；
- 先解析全部条目、DOI 或标题，再决定是否执行；
- 只把父文献条目归入收藏夹，不直接归类 PDF 子附件；
- 写后做回读验证。

这些思想已迁移到 Web API 路线；不同的是，收藏夹 key、写入版本和同步细节都交由 Zotero 服务端处理。

## 不应在缺少前提时重新启用的做法

- 在未知 Zotero 版本、没有完整快照或未定义范围时直接写核心数据；
- 在不理解关联关系的情况下自行生成对象 key，或在全库范围替换 key；
- 在 Zotero 运行时尝试写 SQLite 或绕过锁；
- 将本地附件目录改动误认为服务端文件上传已经完成。
