# 旧式直接 SQLite 路线：归档与禁用说明

这份归档记录旧工具曾经采用的思路，便于审计、迁移和复盘；它不是操作指南，也不包含可以直接写入 Zotero 数据库的脚本。

## 曾经的工作流

```text
计划 JSON（父收藏夹、日期分组、条目 key/DOI/标题）
    ↓
关闭 Zotero，备份 SQLite
    ↓
旧脚本直接 INSERT collections / collectionItems
    ↓
旧脚本自行生成八位对象 key，并手工标记为待同步
    ↓
启动 Zotero 并尝试同步
```

## 这条路线为什么失效

1. 旧代码使用 `A-Z` 和 `0-9` 随机生成 key；其中 `0`、`1`、`I`、`O` 会导致服务端拒绝新对象 key。
2. 即使避开字符问题，直接写库仍绕过 Zotero 对对象版本、缓存、删除墓碑、附件和引用完整性的内部验证。
3. 手工补写同步缓存或同步版本只能“看起来”像本地新增，无法保证服务端同步协议会接受它。
4. 直接把 PDF 复制到 `storage` 目录并插入附件行，不等于完成服务端附件上传。

## 可保留的非危险思想

- 在改变前建立完整备份；
- 将批量任务写成 JSON 计划并先做 dry-run；
- 先解析全部条目、DOI 或标题，再决定是否执行；
- 只把父文献条目归入收藏夹，不直接归类 PDF 子附件；
- 写后做回读验证。

这些思想已迁移到 Web API 路线；不同的是，收藏夹 key、写入版本和同步细节都交由 Zotero 服务端处理。

## 禁止重新启用的做法

- 直接 `INSERT` 或 `UPDATE` Zotero 的 `collections`、`items`、`collectionItems`、`syncCache`；
- 自行生成对象 key 或在全库范围替换 key；
- 在 Zotero 运行时尝试写 SQLite 或绕过锁；
- 用本地附件目录改动替代官方文件上传。
