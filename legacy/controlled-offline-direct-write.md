# 受控离线 SQLite 整理：完整操作契约

这份文档保存既有离线整理方法的可复现工程结构。它面向已经拥有同一版本 Zotero、理解自身资料库结构、并能完整备份和恢复的维护者。

它不是一个“一键修库”教程：仓库不提供可直接对任意资料库写入的脚本，也不建议将此方法用于未知版本、长期无人值守或同步状态不明的资料库。

## 1. 方法的价值

离线 SQLite 方法直接操作本机资料库，因此可以把本地已准备好的题录、分类计划和合法获取的附件作为一个明确批次完成：

```text
输入计划（JSON/CSV）
   ↓
关闭 Zotero → 完整快照 → 只读审计
   ↓
预演：输出拟建收藏夹、拟更新题录、拟归类条目、拟登记附件
   ↓
单批提交（仅计划中的对象）
   ↓
完整性审计 → Zotero UI 抽检 → 一次普通同步
```

在这个边界内，它的优点是：可离线处理、对已有批量数据速度快、可精确控制输入和输出、并能以 dry-run 进行人工复核。

## 2. 每次运行前必须固定的事实

在任何变更前建立一份运行记录，至少写清：

| 项目 | 必填内容 |
|---|---|
| Zotero 版本 | 运行时显示的完整版本号 |
| 数据库架构 | 当前资料库对应的架构版本 |
| 数据目录 | 由 Zotero “设置 → 高级 → 显示数据目录”确认 |
| 目标范围 | 具体计划文件、收藏夹树、条目 key 列表或唯一导入批次 |
| 变更类型 | 建树、题录补全、归类、附件登记、重复项处理中的哪些 |
| 回退位置 | 完整数据目录快照的只读副本位置 |

“帮我整理全部资料库”不是合格范围；应先把任务拆成一个可以抽样核验的小批次。

## 3. 旧工具应具备的功能

一个可维护的旧式工具至少需要以下行为。它们是方法可行性的核心，不是附属功能：

1. **预演默认开启**：不带明确确认参数时，只读取并打印计划，结束时回滚事务。
2. **幂等性**：对于同名且同父级的收藏夹、已有的条目归属和已有的 PDF 附件，重复运行必须跳过而不是重复创建。
3. **输入绑定**：每一条元数据和附件都应绑定到明确父条目，而不是按模糊标题匹配。
4. **父条目优先**：收藏夹成员关系指向文献父条目；PDF 是该条目的子附件，不应被当成独立论文归类。
5. **完整事务**：任何写入要么在同一批次内全部成功提交，要么完整回滚；不能“半成功后继续”。
6. **附件可验证**：登记附件前记录源文件哈希、大小和目标文件名；处理后检查文件存在且父子关系正确。
7. **可读日志**：写入计划、跳过理由、计数变化、异常和审计结果均保存为独立日志。

## 4. 必须理解的内部依赖

直接写入并不只涉及收藏夹或条目表。一个对象的同步可见性还会涉及对象 key、版本、修改时间、删除状态、父子/成员关系、同步缓存，以及附件的本地存储与元数据之间的一致性。

这解释了两个事实可以同时成立：

- 一个受控、针对已知版本和明确数据范围的旧脚本，能在本机正确建立树、补全元数据和整理附件；
- 同一逻辑一旦假设错误的 key 规则、遗漏内部依赖，或在同步前后跨版本使用，就可能被服务器拒绝或留下难以察觉的不一致。

其中对象 key 要避免 `0`、`1`、`I`、`O` 等易混淆字符；但“键看起来合法”并不能替代提交后审计和正常同步验证。

## 5. 最小验证矩阵

每次提交后都要比较前后结果：

| 验证 | 期望结果 | 失败时动作 |
|---|---|---|
| `PRAGMA integrity_check` | 仅返回 `ok` | 停止，关闭 Zotero 后从快照恢复 |
| `PRAGMA foreign_key_check` | 0 条违规 | 停止，不在当前库上继续补 SQL |
| 收藏夹树 | 仅计划中的节点发生变化 | 与计划逐项比较，出现额外变化即回退 |
| 成员关系 | 仅指定父条目增加归属 | 抽查计划首、中、末各一条 |
| 附件 | 目标文件存在、可打开、父项正确 | 停止下一批并从快照回退 |
| 普通同步 | 无新错误 | 保存错误全文，勿按字符批量修补全库 |

## 6. 与 Web API 的协作方式

两条路线不必互相否定：离线工具适合对已知本机批次做诊断、规划和历史维护；Web API 适合后续新增收藏夹、归类、跨设备同步和长期自动化。

推荐的实际组合是：离线审计与输入准备 → 小范围受控维护（仅在确有必要时）→ 后续日常整理改用 Web API → Zotero 正常同步。这样既保留旧方法的效率，也把未来新增数据放在官方支持的接口上。
