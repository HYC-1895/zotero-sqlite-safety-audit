# SQLite 离线审计运行手册

本项目用于本地 Zotero 整理：运行中的 Zotero 通过本地 Connector 导入 RIS/BibTeX；关闭 Zotero 后通过 SQLite 审计建立结构基线；对明确批次使用离线维护操作契约。

## 0. 本地 AI 的启动流程

本机 AI 无需网络或 Zotero API Key。它先让用户在 Zotero 左侧栏选中目标收藏夹，再运行：

```powershell
python zotero_local_connector.py status
python zotero_local_connector.py selected-target
```

第二条命令的资料库和收藏夹就是下一次导入的目的地。AI 应复述该目标，用户确认后再开始预演。

## 0.1 本地导入 RIS/BibTeX

```powershell
# 预演：不会写入
python zotero_local_connector.py import --format ris --file .\examples\example.ris

# 确认目标与文件后导入
python zotero_local_connector.py import --format ris --file .\examples\example.ris --apply
```

Connector 会将题录导入当前在 Zotero 界面选中的资料库或收藏夹。导入完成后，AI 应在界面中抽查题名、作者、年份、DOI/URL 和父条目关系；PDF 由用户在已授权来源获取并作为子附件附加。

## 1. 示例机器目录

在示例 Windows 机器上，Zotero 数据目录为 `D:\Zotero-article`，数据库为 `D:\Zotero-article\zotero.sqlite`，附件位于 `D:\Zotero-article\storage`。这些只是路径示例，不代表其他机器的实际位置。

智能体应在 Zotero 桌面端执行“设置 → 高级 → 显示数据目录”来确认当前目录；不要假设默认目录或从脚本硬编码猜测。

## 2. 运行前检查

```text
[ ] Zotero 窗口和后台进程均已退出
[ ] 已复制完整数据目录，不只是 sqlite 文件
[ ] 目标数据库路径已由用户确认
[ ] 本次任务仅为读取与报告，不会清理、修复或移动附件
```

## 3. 审计命令

```powershell
python zotero_sqlite_audit.py --database 'D:\Zotero-article\zotero.sqlite'
```

报告包含：

- `database_integrity`：应只出现 `ok`；
- `foreign_key_violations`：应为 0；
- `orphan_collection_memberships`：应为 0；
- 活跃条目、收藏夹、附件记录的计数；
- 未同步对象中带有 `0`、`1`、`I`、`O` 的 key 列表，用于定位风险，**不是**批量修改名单。

## 4. 如何理解异常

| 结果 | 解释 | 后续动作 |
|---|---|---|
| 数据库完整性失败 | 文件或结构可能损坏 | 停止；保留快照；使用官方恢复方案 |
| 外键/孤立归属异常 | 旧脚本可能破坏关系 | 停止；不要尝试 SQL 补表 |
| 仅有未同步可疑 key | 曾有第三方生成了不可靠 key 的信号 | 对照云端和来源，使用最小、可验证的恢复流程 |
| 数据库被锁 | Zotero 仍在运行或未完全退出 | 不绕过锁；关闭应用后重试 |

## 5. 为什么不提供“自动修复”

Zotero 的同步状态涉及对象版本、同步缓存、删除墓碑和附件状态。任何单表 SQL 修改都可能在下一次同步时产生冲突或静默丢失。因此，审计结束后应优先采用官方 Web API 进行新写入；对于已经损坏的数据，只能在完整备份、明确对象范围和同步验证下进行一次性最小恢复。

## 6. 旧式离线整理的正确使用姿势

离线 SQLite 路线适合由了解该 Zotero 版本和自身资料库结构的维护者执行。它的关键不是“能否写入”，而是把一次变更限制成可审计、可撤销、可验证的小批次：

1. **锁定版本和范围**：记录 Zotero 版本、数据库架构版本、目标资料库和计划中的条目列表。不要把“全库”作为默认范围。
2. **完整快照**：在 Zotero 完全退出后复制整个数据目录，包含数据库、WAL/SHM（若存在）、`storage`、映射和输入计划。
3. **只读基线**：先运行本项目审计；保存完整性、外键、孤立归属和计数结果，作为变更前基线。
4. **预演**：旧工具必须逐项输出“将创建的收藏夹、将修改的父条目、将加入的归属、将登记的附件、将跳过的重复项”；预演不得写库。
5. **单批提交**：只对已确认的计划执行一次。若涉及附件，先验证每个源文件的哈希、父条目和目标文件名。
6. **提交后复核**：重新运行审计，比较核心计数；用 Zotero 打开库，检查收藏夹层级和随机样本；最后只进行一次正常同步并观察完整错误信息。
7. **异常回退**：任何完整性错误、意外计数变化、同步拒绝或附件缺失都应停止下一批处理。关闭 Zotero 后，用开始前的完整快照恢复，而不是在原库上继续补丁。

## 7. 对象键与同步的特殊说明

收藏夹和条目使用八位对象 key。历史脚本往往会自行生成它们；新对象 key 必须使用不含 `0`、`1`、`I`、`O` 的字符集，且在相应表中唯一。即便键格式正确，也不能证明同步一定安全：对象版本、同步缓存、父子关系、删除记录和附件记录仍需与当前 Zotero 版本一致。

因此，本工具把“含易混淆字符的**未同步** key”标为复核信号，而不是自动修改清单。已同步的旧记录不应因为字符外观而被批量替换。

## 8. 交付物清单

一次合格的离线维护至少应留下：

```text
[ ] 变更前完整数据目录快照
[ ] 输入计划（不包含论文正文或受限 PDF）
[ ] 变更前/后的 JSON 审计报告
[ ] dry-run 输出和实际执行日志
[ ] 变更对象 key、收藏夹层级和条目数的最小清单
[ ] Zotero 打开后的抽样核对记录
[ ] 一次普通同步的结果或完整错误文本
```

这些交付物让旧流程具备可复现性，也使得出现异常时能够准确回退，而不是猜测性地继续写库。
